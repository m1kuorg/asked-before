What the app is

Asked Before turns the questions you keep asking a chatbot into library cards, stamped once for every time you borrowed the answer. A card is stamped returned only after a cold rep: a fresh problem of the same kind, answered without AI. It runs on a made-up demo chat export.

There are two pieces:

  • The page (public/index.html, src/) is plain HTML, CSS, and TypeScript. It reads the export, keeps only your own messages, counts and dates every card in code, and shows one screen at a time: Load, Stack, or Rep.
  • The server (server.ts, server/) is a small Bun program. It serves the page, holds the Anthropic API key, and answers three requests (/api/group, /api/rep, /api/check) by asking Claude Haiku 5.5 for structured output. It stores nothing.

One action: submitting a cold-rep answer

The route through the code

The learner walked these three stops against the source and the browser during the wrap-up.

  1. src/screens/rep.ts → answer(). The answer box's submit handler trims your text, locks the box, and posts { skill, problem, answer } to /api/check. A fail calls rep() again with "Still borrowed" and "The lesson, again". A pass shows "Stamped returned" and a "Back to the stack" button that calls onReturned(date).
    The pass branch 
    const passed = section("verdict", "Returned", reason);
passed.append(el("p", "stamp", `Stamped returned ${date}`));
const back = button("Back to the stack", () => onReturned(date));
  2. server/routes/check.ts → check(), Verdict, SYSTEM. The route rejects a bad body with 400, then sends only that body to the model with the Verdict schema. The schema puts reason before verdict, so the verdict follows from the reason, and SYSTEM requires the reason to name what this answer gets right or wrong.
    The schema 
    // The reason comes first, so the verdict follows from it.
const Verdict = z.object({
  reason: z.string().min(1).describe("One or two sentences to the learner, ..."),
  verdict: z.enum(["pass", "fail"]),
});
  3. src/main.ts → showRep(). onReturned writes returned.set(card.skill, date) into an in-memory Map, then redraws the stack, which strikes that card's margin key and closes its rail. Because the Map lives only in the tab, a reload starts over.

A practice to reuse

Turn a written rule into something you measure on the running app. docs/DESIGN.md's Plate Holds Rule says every state keeps its plate inside the block. At the final review, a browser walk found that the stack's "nothing asked more than once" state had no plate. Adding the plate in showStack() wasn't enough: measuring it at 1920×1080 showed it hanging below the block's foot (plate bottom 359px, block bottom 234px). That led to widening the short-block rule in public/styles.css to every block that holds a plate. The fix then passed the same measurement (block bottom 404px), and bun run check:styles and bun run journey stayed green.

On another project, when a design or product rule says "always" or "never", write down the observable it implies (here, "the plate's bottom is at or above the block's bottom") and check it in the real UI. That's how this check caught a second problem that a code read-through would have missed.
