# Code map

Where each piece of the app lives, which ticket of the spec (m1kuorg/basics#40) owns it, and the seams that let tickets run in parallel without editing the same lines. A ticket that adds, moves, or retires a piece updates its row here. Ticket numbers are issues in m1kuorg/basics.

The app runs on Cloudflare Workers, with its data in D1 and each shelf's sort in a Durable Object (ADR 0005, which supersedes ADR 0003's one Bun process). m1kuorg/basics#60 moved it there: m1kuorg/basics#61 ported the platform, accounts, sessions, API keys, shelves, the throttle, and the daily cap; m1kuorg/basics#62 uploads, the sort, cards, captures, cold reps, and the Desk; m1kuorg/basics#63 your data's download, deleting the account, and `check:migrations`, rewritten for D1; and m1kuorg/basics#64 removed the Bun server and the container image, and brought `check:docs` back. m1kuorg/basics#68 fit it into Workers Free: the SDK derives the password's key (ADR 0006), and daily caps keep it under D1's rows written; m1kuorg/basics#69 kept fresh accounts from draining those caps.

## Layout

The repo is a Bun workspace: the app at the root, and `packages/sdk` and `packages/mcp`. The Claude Code plugin lives in `plugins/asked-before`, and the repo's root is its marketplace.

### The SDK's build

The repo runs the SDK from its sources: the root `tsconfig.json` maps `@asked-before/sdk` to `packages/sdk/src/index.ts`, and Bun follows that mapping at runtime and in its bundler, so the server, the pages, the MCP server, the plugin's build, and the checks never wait on a build. The package's own `exports` point at `packages/sdk/dist`, which only code outside the repo uses, after `bun run build:sdk`. The SDK's modules import each other with `.ts` extensions, which the build rewrites to `.js`, so the built package also loads in Node; a new module does the same.

## Adding an endpoint

1. In `server/api/<area>.ts`, add a handler wrapped in `authed()`: `authed(async (req, { db, params, auth }) => ...)`. Add `{ sessionOnly: true }` for anything a key can't do: renaming, deleting, exporting, keys, and the account. `params` is typed from the path. A handler that sets a cookie puts the `Set-Cookie` line on its own answer.
1. Read the body with `readJson(req, schema)`, a zod schema with a message per field, which answers 400 with the first one. Throw `HttpError(status, message)` for any other failure. A message is shown to the caller, so it never holds phrasing text.
1. Put the SQL in `server/store/<area>.ts`, as async functions that take `db` first and prepare their statements inside, scoped by `auth.userId`, and return the SDK's types. Nothing outside `server/store/` queries `db`. A write that depends on a read goes in one `batch()` with the read folded into its SQL, as `WHERE EXISTS` or `INSERT ... SELECT`, never a read awaited before the write (see [the store](#the-store)).
1. Add the methods and their types to `packages/sdk/src/<area>.ts`; the server's answers use `satisfies` with those types.
1. Prove it in a check script under `scripts/` that starts the app with `startApp()`, and add it to `package.json`.
1. Add its row to the docs page, `src/pages/docs.ts`, which `check:docs` holds to the route table.

Don't edit `server/api/index.ts` or `packages/sdk/src/client.ts` to add an endpoint: both already compose every area.

## Wire conventions

- JSON in and out. A failure is a non-2xx status with `{ error }`; the SDK throws it as `ApiError`, with `status` and `message`.
- Ids are opaque strings (UUIDv7). Times are ISO timestamps over the API and Unix milliseconds in the store.
- A list comes inside an object, as `{ shelves: [...] }`, and the SDK unwraps it. Lists that can grow without bound take a limit and a cursor: they answer a page as `{ uploads: [...], next }`, newest first, which the SDK returns whole, and `next` is the cursor for the page after, or null on the last.
- A phrasing goes over the wire as `{ sourceId, text, time }` and nothing else; a body with any other key is a 400.
- Card status is `"borrowed"`, `"returned"`, or `"borrowed_again"`, from the `card_status` view. A shelf's counts are `{ cards, borrowed, returned, borrowedAgain }`.
- A model failure is a `ModelError`, an `HttpError` with status 502. Past the account's or the app's daily model requests, the model client throws 429; past its daily phrasings, which count every phrasing a chunk carries and each capture, a chunk or a capture is a 429 that stores nothing, and counts toward neither cap. An account made today, a UTC day, sees the app's caps as their lower `firstDay` ceiling, still counted across every account, and its 429 says so.
- A password never reaches the server (ADR 0006): signing up, logging in, and the account's methods send `passwordKey`, or `currentPasswordKey` and `newPasswordKey`, which the SDK derives, and the server takes nothing else. The SDK holds a new password to 10 to 200 characters. A new email changes the key, so `PATCH /account` with an email needs both keys.
- An upload's `messages` counts each of your messages it was sent once, by source id, so a chunk sent twice counts once; its `phrasings` are the ones among them it sorts: those new to the shelf, and any held by an upload still receiving (one whose tab closed, say), which move to it.
- Finishing an upload answers it `waiting` and starts its shelf's sort, one upload at a time per shelf (or answers it `failed`, saying the sort didn't start, when its shelf's Durable Object can't be started, so a retry starts it again): `sorting`, with `offered` of its `phrasings` seen so far, then `sorted`, or `failed` with an `error` safe to show (a model failure, the daily cap's message, or a check that failed three times). `uploads.retry` carries a failed sort on from the first phrasing not yet offered. Each batch is `SORT_BATCH_SIZE` phrasings no sort has seen, plus up to as many of the shelf's most recent unsorted ones; an unsorted phrasing older than that window is compared again only if it falls inside a later batch's window, a known limit the public docs (m1kuorg/basics#51) must state.
- A card is `{ id, shelfId, skill, status, count, firstBorrowAt, lastBorrowAt, returnedAt }`, listed most borrowed first, ties to the later last borrow; `cards.get` adds its `lesson`, its `borrows` (`{ id, sourceId, text, time }`, oldest first), and its `reps`. Unsorted phrasings are those a sort has seen that aren't on a card, newest first; one still waiting for its sort isn't unsorted yet.
- A cold rep is `{ id, problem, answer, verdict, reason, createdAt, checkedAt }`, the last four null until it's checked. `reps.start` answers `{ rep, lesson }`: the lesson is written with the card's first rep and kept, and comes back again until a checked rep passes and after any failed one, else null. `reps.check` answers `{ rep, card }`, the card as the check left it: a pass stamps it returned with the rep's `checkedAt`. A rep is open while it's unchecked and the latest on its card, and only an open rep can be checked. Both ask the model, so both count toward the daily cap, and a failed model request stores nothing.
- A capture is `{ phrasing, card, alreadyCaptured }`: the phrasing recorded, its source id generated and its time the server's clock; the card it landed on as it stands now, or null while it's unsorted; and `alreadyCaptured`, true when the same words, ignoring case and spacing, were captured on the shelf in the last ten minutes, so that capture comes back and no borrow is added. Words matching a phrasing on a card join it without the model; anything else is one sort request at `CAPTURE_EFFORT` (low), with the shelf's cards and the capture first among its `CAPTURE_WINDOW` (50) most recent unsorted. Only the capture moves: onto a card, or into a new card with the unsorted phrasings that ask the same thing; whatever else the answer places waits for the next upload's sort. A failed model request, or a shelf deleted meanwhile, stores nothing.
- The Desk is `{ shelves, totals, mostBorrowed, latestBorrows, latestReturns }`. `totals` has a shelf's counts' shape and equals their sums. `mostBorrowed` holds up to 10 cards not returned (borrowed or borrowed again) in the stack's order; `latestReturns` up to 10 cards with a return stamp, latest first, a card borrowed again since keeping its stamp; each card carries its `shelf` (`{ id, name, demo }`). `latestBorrows` holds the 10 newest borrows by their own time, each with its `card` (`{ id, skill, status }`) and `shelf`.
- Signing up and logging in return `{ account, next }`. `next` echoes the request's `next` only when it's a path inside the app, under `/app/`, and is otherwise `/app/desk`, the app's home, the Desk. The page goes there; m1kuorg/basics#42 serves the app at `/app`, which shows the Desk, and its client routes under `/app/`.
- A cookie-authenticated request that changes something must carry an `Origin` matching the app's origin, and a JSON content type unless it's a bodiless DELETE. The SDK sends JSON on every POST and PATCH, and the browser adds the `Origin`. Signing up and logging in follow the same rule, against forged log-ins, before the throttle counts the try. Either one ends the session the browser already had.
- A Bearer key, when sent, is the only credential considered; the cookie is ignored. A key is `ab_<id>_<secret>`, with a 16-hex-digit id and a 32-hex-digit secret; a bad or revoked one is a 401, and a good one on a session-only endpoint a 403.

## The store

- The database is D1. The schema is the files in `migrations/`, `<4-digit version>_<what>.sql`, which `wrangler d1 migrations apply DB` applies, `--local` for `bun run dev` and the checks and `--remote` for a deploy, recording each in `d1_migrations`. Locally, Wrangler runs each migration, with the insert that records it, as one D1 batch, one transaction, and stops at the first that fails: a failing migration applies nothing, and the ones before it in the same run stay applied, which `check:migrations` proves. Wrangler then prints the error (`✘ [ERROR] ...`) without the failing migration's name; its table leaves that one pending.
- A schema change is a new file with the next version (`wrangler d1 migrations create DB <what>` makes it); never edit one that's merged, since a database that has had it won't take it again. A file is plain SQL and doesn't open its own transaction.
- D1 keeps foreign keys on, and won't turn them off, so dropping a parent table deletes or empties every row beneath it by cascade, even while a migration rebuilds it. Prefer `ALTER TABLE ... ADD, RENAME, or DROP COLUMN`. A table it can't change is rebuilt in one migration that copies its children aside first: `CREATE TABLE keep_reps AS SELECT * FROM reps`, and the phrasings' `card_id`s likewise for the cards table; then drop the `card_status` view, create the new table, copy the rows, drop the old one, and rename the new one to its name; then copy the children back, drop the copies, and make the view again. `PRAGMA foreign_keys = OFF` and `defer_foreign_keys = ON` are taken without an error and change nothing: the cascade still runs. `check:migrations` rebuilds the cards table both ways, and only the recipe keeps the reps and the phrasings' cards.
- Check scripts always start with fresh local state; `bun run dev` keeps its own in `.wrangler/`, which is gitignored like `dist/`.
- Every store function is async. bun:sqlite made every await-free sequence atomic; D1 doesn't, so a read a write depends on goes into the same `batch()`, one transaction, as part of the write's SQL. Starting a session, for one, inserts the session only `FROM users WHERE id = ? AND password_hash = ?`, the hash just checked, so an account deleted or a password changed meanwhile gets none. A statement holds at most 100 bound values and 2 MB per value, and a request at most 1,000 queries: a list of rows goes in as `json_each` statements, one per slice of about 500 KB (`slices()` in `db.ts`), as an upload's chunk and a sort's placement do. A write a row must still be there for folds that in too: a placement holds to the upload it sorts, or the capture it places, with `EXISTS`.
- A capture keeps its `words` beside its text, trimmed, with each run of spacing one space, and lowercased, so that its insert checks, in SQL, that the same words weren't captured on the shelf in the ten minutes before. An export's phrasing has none.
- Every child table cascades on delete from its parent. A phrasing's `card_id` is set to null when its card goes, which leaves it unsorted.
- `upload_messages` keeps the source id of every message an upload was sent, once each: its count is the upload's `messages`.
- `card_status` gives, per card, `borrows`, `first_borrow_at`, `last_borrow_at`, `returned_at` (the latest passed rep's `checked_at`), and `status`, comparing timestamps rather than dates, so a borrow sent in the same millisecond as a pass leaves the card returned.
- A card's `lesson` is written once, by its first rep, and never replaced. A rep's `answer`, `verdict`, `reason`, and `checked_at` are written together, once, only while it's the latest on its card; ids are time-ordered, so the latest is the greatest `(created_at, id)`. Reps cascade with their card, so deleting an upload that removes a card removes its reps.
- `usage` counts model requests and phrasings per account per UTC day, and `site_usage` both for the whole app; `spendModelRequest()` and `spendPhrasings()` in `store/usage.ts` are the only writers, and only ever raise a count.
- `users.password_hash` holds `sha256$<salt>$<hash>` of the account's password key (`server/passwords.ts`) since migration 0004; `0001`'s comment, scrypt, is out of date, and an account made before can't log in.
- Sessions store the SHA-256 of the cookie's token. An API key's secret is stored the same way, in `api_keys.secret_hash`, and only `keys.create` ever returns the whole key. A key's `last_used_at` is written at most once a minute.

## Pages

- `PAGES` in `scripts/build-pages.ts` lists each page's HTML file under `public/`. `bun run build:pages` bundles them with their scripts, styles, and fonts into `dist/`, which the Worker's static assets serve, each at its name without `.html`; the Worker itself answers only `/api/`. Pages are served to be revalidated every time, and the hashed assets under `/assets/` as immutable, with the security headers from `_headers`.
- There's no hot reload: run `bun run build:pages` again to see a change to the page, and `wrangler dev` serves it.
- The pages: `/` (`index.html`, the landing page), `/docs` (`docs.html`, the docs page, mounted by `src/pages/docs.ts`), `/login` (`login.html`), `/signup` (`signup.html`), and the app at `/app` and `/app/*` (`app.html`, by `_redirects`). Any other path gets `not-found.html` with a 404, and anything under `/api/` gets `{ error }`. A new page adds its HTML file under `public/` and a line in `PAGES`; the landing page and docs already have theirs.
- A public page's navigation is static markup in its HTML: the product name, Docs, then Log in and Sign up. Copy it from `login.html`, marking the current page with `aria-current="page"`.
- The content security policy allows only the app's own origin, for workers too: the export readers inflate a zip in the page, with fflate's synchronous `Inflate`, so no `blob:` worker runs. Inline scripts, `<style>` elements, and `style="..."` attributes in markup are blocked, so style through class names and the stylesheets.

## The app page

`app.html` loads `src/app/main.ts`, which asks `auth.me()` who is logged in, draws the top navigation (`src/app/nav.ts`), and starts the router (`src/app/router.ts`). The page reaches the server only through the SDK client in `src/app/client.ts`, which sends any 401 to `/login?next=<where you were>`; logging in goes back there. Log in and sign up (`src/pages/`) follow the server's `next`.

A screen is `(root: HTMLElement, props: ScreenProps<"param">) => void | Promise<void>`. The router empties `#app`, sets `#app[data-screen="<name>"]` and the page title, marks the navigation's section, and mounts the screen with:

- `params` (decoded `:params`, typed from the path) and `query`;
- `client` (the SDK), `account` (who is logged in), and `setAccount`, which a screen calls after changing the name or email so the navigation shows it;
- `navigate(path)`, though plain `<a href="/app/...">` links are followed without a reload anyway;
- `signal`, aborted when the learner leaves, so nothing a screen was still fetching draws over the next one. `load()` from `src/parts/frame.ts` checks it for you.

A screen's own views (such as a shelf's unsorted phrasings, or one upload's progress) can live in its `query` rather than in a new route.

## Check scripts

- `startApp(env?, { state?, port?, root? })` from `scripts/lib/app.ts` checks for Node.js 22 or later, which Wrangler needs, builds the pages into a folder of their own, applies the migrations to fresh local state in a temporary folder, and starts `wrangler dev` there on a free port, and returns `{ url, databasePath, log, workerLog, browser, stop, kill }`. `env` sets the Worker's vars, such as `DAILY_MODEL_REQUESTS` or `ANTHROPIC_BASE_URL`, always with an empty `PUBLIC_URL` unless it gives one, and every daily cap lifted unless it sets one, since the checks make more model requests and send more phrasings than a learner's day allows, and `wrangler.jsonc`'s vars are the deployed app's. `browser(address)` calls from that address, as Cloudflare names the caller in `CF-Connecting-IP`, which `wrangler dev` sets to this computer's address when a request has none. `state` starts it on that folder's state, which `stop()` keeps, and `port` (from `freePort()`) keeps one address across starts. `kill()` sends Wrangler and its workerd SIGKILL, by the process group the helper started, as a crash would, then cleans up as `stop()` does. `root` starts a copy of the app from another folder, as `check:migrations` does. `databasePath` is the local D1 database's SQLite file, which a check may open with bun:sqlite, read-only, with three documented exceptions: `check:captures` writes one capture's time 11 minutes back, to age it past the ten-minute repeat window, and `check:fresh-accounts` one account's `created_at` a day back, to age it past its first day, since both are the server's clock, which no endpoint sets, and the only other way there is a wait; and `check:caps` adds a trigger that fails any update lowering an account's count, since no endpoint can make the database fail a write. `log()` is all of Wrangler's output: its own lines start with `[wrangler:`, after a banner that ends `Ready on <url>`, and the Worker's say only a request's method, path, status, and duration; `workerLog()` splits the Worker's into those request lines and any others. Locally, nothing runs the cron on its own: a check runs it with `fetch(`${app.url}/cdn-cgi/local/scheduled?cron=...&time=<ms>`)`, Wrangler's route for it, whose `time` sets the run's `scheduledTime`. The helper passes `--test-scheduled` only to quiet Wrangler's warning that crons don't run locally; that flag's own path, `/__scheduled`, is the static assets' here, since only `/api/*` reaches the Worker first. Wrangler finds `ANTHROPIC_API_KEY` in `.env` or the shell, as the checks do.
- `SORTER_FAULT` is a check's hook into the sort's Durable Object, like `ANTHROPIC_BASE_URL` for the model, never set otherwise: `start` makes every `start()` throw, as a Durable Object out of reach would, and `database` every query its alarm makes fail, as a database out of reach would. `check:sort-rules` sets it.
- `bun run journey` walks the whole product with nothing stubbed, in the browser, then through the SDK and the MCP server, as the README describes; change it when a screen it walks changes.
- Finishing an upload starts a sort, which asks the model. A check that doesn't prove the sort's quality starts a model stand-in, `startModelStub(reply(keySorter))` from `scripts/lib/`, and passes its `url` as `ANTHROPIC_BASE_URL` to `startApp()`, so it needs no key and its sorts end as the answer key says. The stand-in also holds, refuses, or reads requests, for a check of waiting and failure states or of what the model is sent.
- `app.browser()` is one browser: an SDK client that keeps its own session cookie and sends the app's `Origin`. `cookie()` gives its Cookie header for requests made without the SDK. A script can also make a key with `keys.create` and reach the API as a script or agent would, with `createClient({ baseUrl: app.url, apiKey })`.
- Each copy of the app allows 20 sign-up and log-in tries per network in 15 minutes, so a script making many accounts should start its own copy, or call from many addresses with `app.browser(address)`.
- The model stand-in listens on `127.0.0.1`.
- A browser check stubs a request only inside the script, with Playwright's `page.route`, never in the app.
- `check:styles` signs up one learner on a fresh copy of the app, then runs every module in `scripts/styles/`, in name order. A module's default export is `(kit: Kit) => Promise<void>` (`scripts/lib/styles.ts`): it opens pages with `kit.page({ loggedIn })` and `kit.open()`, drives them into each state, and calls `kit.shoot(page, name)`, which saves the screenshot and checks the type floor, vermilion, radius and shadow, the inks, contrast, the plate count, a plate ending inside the block's padding, and sideways scroll. A waiting or error state passes `{ plate }`: true once the screen has its count, false while it waits for that count, as `docs/DESIGN.md`'s Plate Holds Rule says. A surface's ticket adds its own module rather than editing another's. `shell.ts` and `parts.ts` are m1kuorg/basics#42's; `stack.ts` drives the real shelf page (m1kuorg/basics#45), `rep.ts` the real card page (m1kuorg/basics#46), queuing the model stand-in's answers to its rep and check requests through `kit.model`, `desk.ts` the real desk (m1kuorg/basics#47), which runs first and needs the learner without shelves, and `docs.ts` the docs page, logged out (m1kuorg/basics#51). Modules share one learner, so one that makes a shelf deletes it before it ends.
- `check:styles` starts its app with the model stand-in answering as the answer key sorts (`keySorter`), so a module can upload the demo export and get the key's cards, with no key and no wait.
